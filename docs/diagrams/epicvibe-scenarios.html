Two ways an order gets from a conversation into Epic

One path runs while the EHR is down and writes back later over HL7v2. The other runs inside Epic through CDS Hooks and a SMART app, and never writes an order itself. Both share the same catalog-grounded proposal engine. The drawings separate what we have verified on our own demo stack from what we believe about Epic's side of the line.

verified on the local stack believed, from Epic documentation or the spike tested and not possible
Scenario A · EHR offline

Transcript to template to HL7v2 batch

No chart is available, so the transcript is the only source. Everything the clinician signs is held durably and released as ORM^O01 messages when the integration engine can reach Epic again.

Sequence

  1. The transcript is pasted or streamed in. No chart lookup happens; the encounter may not exist in Epic yet.
  2. The model picks one template from the local library and lists alternatives with confidence.
  3. Every field is filled only from the transcript, each carrying a verbatim quote. Unknowns stay blank and are flagged.
  4. The clinician edits, deselects deferred defaults, and signs. The set moves to the durable queue.
  5. When connectivity returns, the sender builds one ORM^O01 per set and delivers it over MLLP.
  6. ACK closes the order. NACK or silence lands the set on the recovery worklist for manual entry.

Verified local stack

  • Six transcripts select the right template and fill 6 to 8 of 9 patient fields with evidence.
  • Signed sets survive restarts; stuck sends recover to queued.
  • ORM messages escape HL7 delimiters and round-trip ACK, NACK, and timeout against the mock engine.

Believed to confirm

  • Bridges accepts inbound ORM for all order types once the customer builds the interface.
  • Downtime temp ids reconcile to MRNs through a manual step, not automatically.
  • Hosted-model extraction needs a data agreement, since transcripts carry the patient's name.
Scenario B · inside Epic

CDS Hooks card plus a SMART app that hands back

Epic fires hooks as the clinician works. The service uses everything Epic will share, proposes an order set grounded in the customer's catalog, and returns it as a card. The SMART app shows the fully pre-populated template but never writes an order; it hands its edits back so the next card carries them.

Sequence

  1. Chart open fires patient-view with prefetch. The handler answers empty at once and queues the proposal job.
  2. The job reads anything prefetch left out, summarizes without identifiers, asks the model, and drops any item not in the catalog.
  3. Order entry fires order-select. The card offers one create action per item, advisory values in the text, and a SMART link.
  4. Accepting a suggestion makes Epic file an unsigned order from its own orderable defaults. Epic reports the outcome to our feedback endpoint.
  5. Opening the link launches the Order Assistant with the patient context. It reads the full chart and shows the pre-populated template.
  6. "Send to order entry" stores the edits in the cache. Back in Epic, the next order-select card carries them; order-sign flags anything missed.

Verified mock EHR

  • All three hooks, prefetch resolution, async job, and card rendering for three different patients and order sets.
  • SMART EHR launch with OAuth, full chart pull, pre-populated template with evidence.
  • The model is never on the synchronous hook path; malformed input returns an empty card set.

Believed from Epic docs and the spike

  • Epic files unsigned orders from accepted suggestions and ignores dose, route, and frequency in the payload.
  • No SMART Web Messaging into the cart; FHIR order creates fail outside a hook (403 on ServiceRequest, 405 on MedicationRequest, tested).
  • The unsigned-order Update systemAction may allow annotating orders Epic already filed; not yet tested.
